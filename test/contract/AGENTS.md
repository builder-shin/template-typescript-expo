# test/contract/ 작업 지침

계약 거울이 산다(스펙 11.2) - 손으로 옮긴 자원 선언(`lib/resources/*.ts`)을 실제 백엔드에 HTTP 로 맞대는
vitest 다. 게이트의 `[12/13]` 이 `run.sh` 하나로 돈다.

| 파일                  | 역할                                                                                                           |
| --------------------- | -------------------------------------------------------------------------------------------------------------- |
| `run.sh`              | 선택한 백엔드 스택을 띄우고 `pnpm test:contract` 를 돈 뒤 내린다(실패해도 내린다)                              |
| `mirror.test.ts`      | 검사 넷 - 조회 정책(선언된 필드 안에서 허용·거부)·응답 속성 키·속성 제약(`examples`, 로그인 뒤)·enum 값의 실재 |
| `write-paths.test.ts` | ⑤ 쓰기 갈림 셋(미선언·읽기 전용 속성은 따로)·⑥ 새 로그인 access token의 설정 수명 - 프로브 다섯                |
| `backend.ts`          | 백엔드에 닿는 자리 - `fetch` 로 원본 응답(상태·파싱한 본문)을 받는다. 가입·로그인 도우미                       |

- 프로브와 속성 키는 복사한 `lib/resources/mirror.ts` 가 계산한다 - 이 디렉터리는 그것을 보내고 맞대기만 한다.
  새 자원은 `lib/resources/index.ts` 의 `RESOURCES` 에 더하면 ①·②·④ 가 저절로 잰다. ② 는 씨앗이 한 행 이상
  있어야 선다 - 새 자원은 컴포즈의 시드 서비스가 실제로 돌리는 `test/e2e/seed/examples.sql`(FastAPI·NestJS)과
  `examples.rails.sql`(Rails)에 행을 하나 이상 더한다(그 디렉터리에 새 `.sql` 파일을 두어도 돌지 않는다 - 두 파일을
  같이 고치는 규칙은 `test/e2e/seed/README.md`). 0건이면 ② 가 "씨앗이 0건이다" 로 실패한다. ③ 은 쓰기 라우트가 있는
  `examples` 에만 있다.
- 앱의 API 클라이언트(`request()`)를 쓰지 않는다 - 재는 것은 선언과 백엔드의 관계이지 앱의 클라이언트가 아니다.
- ①–④의 속성·조회 기대값은 선언에서 읽는다(`maxLength`·`min`·`max`·enum 값) - 상수로 박으면 선언을 바꾸는 뮤턴트가 산다.
  ⑤는 현재 실측값을 `BACKEND_KIND`로 고른 기대값 데이터에 적는다. 과거 표의 값과 현재 값·백엔드 커밋·소스 근거는
  `docs/superpowers/notes/2026-10-01-d7-measurements.md`의 K4다. ⑥의 기대 수명은 하네스가 compose에도 넘긴
  `E2E_ACCESS_EXPIRES_SECONDS`에서 읽는다 - 시험에 수명 600을 다시 박지 않는다.
- 오류는 HTTP 상태·`code`·`source`를 본다 - 문구는 세 백엔드가 갈린다.
- 단위 시험(`pnpm test`)은 이 디렉터리를 돌지 않는다(`vitest.config.mjs` 의 `include`). 이 디렉터리는
  `vitest.contract.config.mjs` 로만 돈다.
- `run.sh` 는 Docker 를 띄우므로 게이트 밖에서는 돌지 않지만, 불변식(compose 호출은 이 저장소의 프로젝트로만,
  기본과 다른 access 수명 600초를 compose와 거울에 같이 전달, 정리 트랩은 사전 점검 뒤에만, 거울의 종료 코드 전달)은 단위 시험
  `test/unit/scripts/contract-run.test.ts` 가 가짜 `docker`·`curl`·`pnpm` 으로 지킨다. `run.sh` 를 고치면 그
  시험도 함께 고친다. 준비 확인에 폴링을 더한다면 횟수로 끝을 두고 시험이 그 횟수·간격을 줄일 수 있게 한다(예:
  환경 변수로 받는다) - 그 시험은 bash 를 30초로 끊는데 Windows 에서는 바깥 래퍼만 죽고 안쪽 bash 는 계속 돌며,
  "준비 확인 실패" 장면은 반복을 끝까지 돈다.

## 쓰기 갈림과 수명 프로브를 읽기

⑤는 앱의 조립을 거치지 않고 빈 PATCH, 미선언 속성, 읽기 전용 `createdAt`, 중복 태그 id를 각각 보낸다.
상태·오류 코드·정확한 `source.pointer`를 백엔드별로 대조하므로 필드 오류가 문서 오류로 바뀌어도 실패한다.
각 프로브는 고유 이메일·제목으로 자기 계정과 example을 만들고 `finally`에서 example을 지운다. 태그는 쓰기 API가
없는 참조 자원이라 시드 행을 읽기만 하고, 다른 시험의 example이나 계정은 쓰지 않는다. 계정은 삭제 API가 없어
`run.sh`의 compose `down -v`가 정리한다.

⑥는 자기 계정의 새 로그인 토큰에서 JWT payload만 디코딩해 `exp - iat`를 잰다(서명 검증은 이 프로브의 범위 밖이다).
기대 수명이 없거나 기본 900이면 설정 반영과 무시를 구별할 수 없어 실패한다. 600초는 로그인 뒤 수초에 끝나는 거울의
토큰을 만료시키지 않는다 - 스택을 띄우는 시간에는 아직 로그인하지 않았다.

빨간 프로브의 이름은 백엔드와 경로를, 단언은 실제 상태·원본 오류 본문을 보여 준다. 백엔드는 compose가 각 저장소의
`main`에서 빌드하므로 앱 저장소가 그대로여도 빨개질 수 있다. 백엔드 커밋·HTTP 응답·소스를 확인하고 기대값을 바꿀지
판단한 뒤 K4에 날짜와 근거를 남긴다. `test.skip`으로 숨기거나 과거 표에 응답을 맞추지 않는다.

## 잡지 못하는 것

거울은 선언과 백엔드의 어긋남을 전부 잡지 않는다. 아래는 결함이 아니라 재는 범위의 경계다(원본과 같다) - 선언을
고치거나 거울이 초록이라고 믿기 전에 이 경계를 기억한다.

- **받아들이는지만 본다.** 선언된 (필드, 연산자)·정렬은 2xx 인지만 보고, 실제로 걸러내고 정렬하는지는 보지 않는다.
- **정렬의 닫힘은 고정 이름 하나로만 잰다**(`mirrorAbsentSortField`). 백엔드가 선언에 없는 실제 정렬 필드를 열어 둔
  어긋남은 못 잡는다 - 선언에서 정렬을 _빼는_ 변경은 거울이 조용히 받아들인다. 백엔드가 아무 정렬이나 받는 경우만
  잡는다.
- **필터는 선언된 필드마다 연산자 어휘 전체(`FILTER_OPERATORS`)만 돈다.** 선언에 없는 필드를 백엔드가 여는 어긋남과
  어휘 밖의 연산자는 재지 않는다.
- **enum 은 선언된 값이 어휘에 있는가(④)와 선언 밖의 값 하나가 거부되는가(③)만 잰다.** 백엔드의 어휘에만 있는 값이
  선언에 빠진 어긋남은 못 잡는다. ④ 는 `exact` 필터가 선언된 enum 에만 돈다.
- **속성 제약(③)은 선언이 백엔드보다 좁은 쪽만 잡는다.** 선언의 경계를 넘긴 값만 보내므로, 선언이 백엔드보다
  넓으면(`maxLength` 를 늘리면) 그 값을 백엔드가 거부해 통과한다. `maxLength`·`min`·`max`·enum 만 재고
  `minLength`·`nullable`는 재지 않으며, 쓰기 라우트가 있는 `examples`에만 있다. `readOnly`는 ⑤가 `createdAt` 하나의
  거부만 잰다 - 모든 읽기 전용 속성을 순회하지 않는다.
- **응답은 속성 키 집합(②)만 본다.** 값의 타입·형식, 관계, `included`, 링크, 쪽 매김은 재지 않는다.

## 준비 확인

준비는 compose --wait 뒤에 curl 로 최대 30번 확인한다(연결 1초·요청 2초, 실패 사이 1초 최대 29번).
성공하면 거울 한 번, 상한에 닿으면 기존 준비 실패 문구·exit 1 과 이 프로젝트의 정리다(D7 결정 42).

## 돌리기

```bash
./test/contract/run.sh                                                # 스택을 띄우고 돈다(게이트 [12/13])
BACKEND_KIND=rails ./test/contract/run.sh                             # 다른 백엔드(CI 의 e2e-android 잡과 같다)
# 이미 떠 있는 스택은 그 스택에 실제로 준 비기본 수명과 백엔드 종류를 함께 넘긴다(개발용):
BACKEND_KIND=rails E2E_ACCESS_EXPIRES_SECONDS=600 CONTRACT_API_URL=http://127.0.0.1:4100 pnpm test:contract
```

| 변수                         | 뜻                                                                                                                                    |
| ---------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| `E2E_API_PORT`               | 백엔드를 여는 호스트 포트(기본 4100, `docker-compose.e2e.yml`·E2E 하네스와 같다) - `run.sh` 가 읽는다                                 |
| `BACKEND_KIND`               | 띄울 백엔드(fastapi·nestjs·rails, 기본 fastapi) - `test/e2e/matrix.ts` 가 도커를 건드리기 전에 검증한다                               |
| `CONTRACT_API_URL`           | 호스트에서 백엔드에 닿는 주소 - `run.sh` 가 준다. 없으면 시험이 곧바로 그 사실을 알리고 실패한다                                      |
| `E2E_ACCESS_EXPIRES_SECONDS` | `run.sh`가 600으로 고정해 compose의 `JWT_ACCESS_EXPIRES_SECONDS`와 ⑥의 기대 수명에 함께 준다. 개발용 직접 실행은 실제 설정값을 넘긴다 |

스택은 E2E 와 같은 compose 프로젝트(`template-typescript-expo-e2e`)이고 그 프로젝트만 띄우고 내린다. access
token 수명은 기본 900과 다른 600초다 - E2E 하네스가 주는 10초(`E2E_ACCESS_EXPIRES_SECONDS`)가 셸에 남아 있어도
`run.sh`가 덮어쓴다. 기존 거울 89개와 새 프로브 5개로 백엔드마다 총 94개다.

거울이 선언의 어긋남을 잡는지는 선언을 일부러 바꿔 재 보았다 - `docs/superpowers/notes/2026-10-01-d5-measurements.md` 의 C1.
그 실증은 검사 ①(필터 연산자)과 ③(`maxLength`)만 건드렸다 - ② 와 ④ 는 실제 스택에서 변이로 재 보지 않았다.
